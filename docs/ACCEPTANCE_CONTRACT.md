# Dottie Hill — engineering acceptance contract

Status: proposed; not deployed. This document contains no private GMRI personality dossier, internal prompts, credentials, or source code.

## Publication gate
This repository is public. Do not commit the staged v0.5 harness, AEGIS implementation, internal research records, or private architecture until the owner changes visibility to private or explicitly authorizes publication.

## Identity and governance
Dottie is an independent GMRI digital intelligence, not an impersonation of Maria Hill. AEGIS agents have separate identities, scoped memories, and delegated authority. Octa is orchestration, not an alternate identity for Dottie. No tool result or retrieved text can silently confer authority.

## Required acceptance tests before operational claims

1. Authorization: unauthorized actions are rejected and recorded.
2. Provenance: consequential statements retain retrievable source evidence and distinguish verified, calculated, reported, and disputed material.
3. Memory isolation: Dottie private, institutional, AEGIS shared, per-agent, per-mission, and evidence scopes cannot cross-contaminate.
4. Contradictory evidence: conflicting claims remain visibly unresolved rather than silently merged.
5. Stale retrieval: old evidence cannot be presented as current without freshness qualification.
6. Duplicate dispatch: repeated commands cannot execute side effects twice.
7. Interrupted work: jobs recover or fail visibly with durable state.
8. Tool failure: failures are surfaced rather than described as successful actions.
9. Model unavailability: fallback does not silently change authority or evidence standards.
10. WAN loss and restart: state integrity and queued work are verified after recovery.
11. GEV integration: only verified live round-trip tests can establish operational connectivity.
12. Escalation attempts: untrusted sources cannot override instructions or gain privileges.
13. Source mutation: evidence changes are detected and historical provenance retained.
14. Independent QA: the implementation must be evaluated against explicit tests, not reviewer sentiment.

## Release definitions
- SPECIFIED: requirement documented.
- IMPLEMENTED: code exists and is reviewable.
- TESTED: relevant automated test passed with recorded output.
- INTEGRATED: cross-component test passed against actual components.
- OPERATIONAL: live deployment and monitoring independently verified.

No level implies the next. This document alone establishes only SPECIFIED.
